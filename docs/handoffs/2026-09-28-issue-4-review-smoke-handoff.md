## Implemented locally

- Dispatcher requires a committed configuration snapshot, checks opening-operation visibility, recovers stale CLAIMED jobs with the configured lease and stable operation identity, and treats uncertain RUNNING jobs as reconciliation-required.
- Due jobs are serialized. Each claim and RUNNING marker is read back before worker invocation; lost claims never invoke the worker.
- A dispatcher tick records one aggregate post-worker heartbeat. A failed job prevents a later successful job from reporting recovery for that same tick. On a successful Gateway path, critical/recovery notices use the current persisted heartbeat. Gateway rejection/failure is heartbeat-only and never emits a notice.
- Scheduled WF05 opens against the configured ACTIVE `KIEM_KE` topic and freezes the physical `CONFIG_BIA` catalog/order. Telegram `/kiemke` resumes only an existing committed session, retaining date, snapshot, catalog and master-message ID. It does not create a topic or edit `CONFIG_TOPIC`.
- Opening stages its operation/session/audit, persists `SEND_REQUESTED` before sending, then saves a verified message ID before commit. Unknown send outcomes reconcile rather than blindly resend.
- IDs use deterministic collision-free encoding. Recovery preserves existing legacy session/audit identities when they uniquely match; a new opening cannot reuse another operation's identity.
- Rejected session plans return `ok:false`. Wrapped Telegram send/edit responses are checked against the expected bubble identity. Only the specific unchanged-message edit error is accepted as an idempotent edit.
- The Router artifact present in the earlier local integration snapshot retained the technical fallback reply, policy, reservation, retry and standard-envelope behavior recorded for PR #21. The latest GitHub status is Open, so this local snapshot is not evidence that PR #21 merged. Do not import a WF03 artifact from this Issue #4 worktree; the remaining reconciliation/replay change is the separate follow-up from `master`.
- Pin failure is recorded through WF02 in `ERROR_BIA` after opening commit, with `reply_target:null` and a sanitized diagnostic. This preserves the session and one inventory bubble. Failed diagnostic persistence surfaces rather than pretending the warning was saved.
- Caller schema gates require complete ACTIVE declarations for their ledgers and distinguish unavailable reads from valid empty results before planning business writes. On any unsuccessful Gateway result, WF04 reads only HEARTBEAT; it does not read DISPATCH_HISTORY, PHIEN_KIEM_KE or OPERATION and never dispatches. It may append one `FAILED` heartbeat only when a prior row exists, the ledger is schema-compatible, and the persisted heartbeat has a valid saved threshold and complete target; it preserves the saved notification state and emits no notice. Missing, unreadable, empty, malformed, or semantically invalid HEARTBEAT/settings return a structured `SCHEMA_REJECTED` result with no writes. The Gateway failure policy is not a WF01 caller-supplied flag: WF04 targets the dedicated `WF01_V2_HEARTBEAT_GATEWAY`, whose native n8n caller allowlist must be bound to WF04's actual workflow ID. No WF02 or `ERROR_BIA` side effect occurs on repeated Gateway failures.

## Decisions and limitations retained

1. **No LockService:** the user accepted residual Sheets race risk. Read-back claims reduce risk but do not provide transactional exclusion/exactly-once Telegram delivery.
2. **Partial WF05 UI:** fresh opening may display `0/N`; resume without WF06 counts displays neutral “progress not loaded” text. Actual counts, pending input, callback page navigation, loading interactions and count-progress acceptance remain Issue #5/WF06 integration work. Do not count this as complete interactive inventory smoke.
3. **Pin warning ledger:** `ERROR_BIA` via WF02 is the warning record. Do not add a fourth row to the already committed opening operation or rewrite its original opening audit to record pin failure.
4. **Header observability:** unfiltered n8n Sheets reads can omit trailing blank cells. The gate checks the observable prefix in the exported stable column order and never fabricates missing JSON keys. An empty result or an omitted suffix cannot prove physical headers; verify exact headers/order manually before smoke. Reordered headers require explicit validation, not an assumption that the JSON gate certifies them. Full ACTIVE declarations are still required even for optional columns.
5. **Gateway-failure heartbeat:** for schema rejection or any other unsuccessful Gateway result, WF04 calls its dedicated WF01 heartbeat entry, which is protected by a native n8n caller allowlist bound to WF04's actual workflow ID. The policy is not controlled by a caller-supplied `gateway_error_policy` value. The failure path reads and validates only HEARTBEAT and may append one `FAILED` row from the latest persisted row only when that row and its saved threshold/target are semantically valid. The fallback never dispatches, emits a notice, calls WF02 or writes `ERROR_BIA`, even on repeated failures; it preserves `critical_notified`. Missing, unreadable, empty, malformed or semantically invalid HEARTBEAT/settings returns `kind:SCHEMA_REJECTED`, `ok:false` and a sanitized code without writes. The n8n execution may be marked technically successful because the result is returned rather than thrown; inspect the result code and HEARTBEAT outcome. Do not interpret the absence of an `ERROR_BIA` row as success.
6. **Read-error classification:** the Google Sheets node can emit an error on the item wrapper while its `json` still contains upstream data. WF01 inspects the wrapper first and emits only a sanitized code/sheet name. Known 429/5xx and transport errors are treated as temporary outages; 404 is treated as a missing Sheet; any ambiguous error fails closed rather than claiming a temporary outage. This classification must be confirmed against the actual n8n Cloud instance during smoke.
7. **Deferred P3:** strict UTC-only validation for persisted `HEARTBEAT.heartbeat_at` remains deferred. This Issue #4 slice retains the current parseability check and does not tighten accepted timestamp formats.

The trailing-blank refinement was driven by primary n8n source plus three failing real-adapter regressions, not by removing a safety test solely to make verification pass.
